# PR-4 设计稿：结果回飞书 + 四种失败的人话

> 状态：**已实现（2026-11-18，`docs/HISTORY.md` 有收工记）**。前置：PR-1（v10/角色）、PR-2（`Workbench` + 交接单）、PR-3（`work` 事件 + `dsh-worker`）。
> 这一段做完，S3a 的闭环就通了：**群里要活 → 你批 → 真有人干 → 结果带着引用回到群里**。

---

## 1. 这一段要解决什么

PR-3 之后，活真的干了，结论也落账了——但**群里、私聊里什么都没发生**。主人看不到结果，也看不到"为什么没干成、怎么接手"。

PR-4 补的就是最后一跳：**把结论和交接单送回飞书，而且只走 outbox 这一条出口**（§出口唯一）。

## 2. 回哪儿、说多少（三类消息）

| 情形 | 群 | 私聊 |
|---|---|---|
| **成功**（`done`） | 一句结论 + 产物清单（≤800 字），**引用原消息** | 不发（除非产物超长，把完整清单落一行路径） |
| **失败**（`failed`：超时 / 机器睡过去 / 其它） | 一句人话 + 「卡在哪」+ 「完整交接单私聊给你了」，**引用原消息** | 完整交接单（`handoff.md` 全文按段切条发） |
| **被拦住**（`blocked`：锁冲突 / 凭证 / 工具起不来） | 一句人话 + 「等你答复」，**引用原消息** | 完整交接单 + **一个问题**（见 §5） |

**引用原消息**指 `outbox.kind='say'` 且 `parent_id = tasks.origin_mid`——不是新开一条，也不是另起话题。

## 3. 顺序与幂等（这一段最容易出事故）

```
跑完 → ① 写 outbox（queued，uuid='work-result:<task_id>[:<attempt>]'）
     → ② 写 tasks 状态与 note
     → ③ ack work 事件
```

- **先 enqueue 再 ack**：outbox 是唯一出口且是耐久的。若在 ① 之后崩溃，事件租约到期会被重领，重领时先按 uuid 查重
  （已存在就不重复入队），**不会重复刷屏**；若反过来（先 ack 再发），崩溃就会让结论永远丢在账本里
- 头部注释里要写清这个顺序的理由（这是本仓最容易在重构时被"顺手调换"的地方）
- 群里那条 `say` 与私聊那条 `say` 用不同 uuid（`work-result:<task_id>:group` / `:dm`），各自幂等

## 4. 群里那句话怎么写（人话，禁用系统词）

**成功**（示例）：

```
三份 csv 汇总好了：一共 128 行、7 个字段，按项目分了 5 类。
产物在 worktree 里：…/work/tsk_xxx/artifacts/summary.csv
（这张表我没有直接发到群里，你确认没问题我再发。）
```

**失败**（示例）：

```
这件活没干完：超时了，卡在「调用工具 str_replace」。
完整交接单已经私聊给你，里面有需求原话、做过哪几步、产物路径、工作空间，以及接着干的命令。
```

**被拦住**（示例）：

```
这件活我没法动：那个会话你正开着。
你把它关掉之后回我「继续」，我再试一次。
```

禁用词照旧：`账本 / 审计 / 链路 / running / hints / outbox / approval / state= / schema / 迁移 / 幂等 / release / sqlite`。

## 5. `blocked` 之后怎么接得上

被拦住不是终点，得有出口：

- 私聊那条带**一个问题**（`open_question`），例如「把那个会话关掉之后，回我「执行」，我再试一次」
- 主人回 **「执行」**（唯一一张时）或 **「执行 2」**（多张卡住的活时）→ 产生 **attempt+1** 的新 `work` 事件
  （`dedupe_key='work:<task_id>:<attempt>'`），任务从 `blocked` 回到 `running`
- 最多重派 3 次（`worker.max_attempts`），超了就把任务置 `failed` 并在群里说明「试了 3 次都卡住，先别派了」

> **偏差（2026-11-18，Lead 定）**：原稿让主人回「继续」，落地时改成复用已有的 **`执行`**。
> 理由：命令词每多一个，说明书、测试、主人要记的东西都要跟着长；而「执行」本来就有
> 「把它推去开工」的语义，用在被拦住的活上正好。群里/私聊的文案因此统一成「回我「执行」」。
> `状态` 命令现在也会把卡住的活带编号列出来（`Store.blocked_queue()`，与待批卡同一套编号口径）。## 6. 四种失败的人话（固定文案，一处定义）

| `kind` | 群里那句 | 私聊的问题 |
|---|---|---|
| `timeout` | 「超时了，卡在 <最后一步>」 | 无（交接单里有"接着干"的命令） |
| `no_final` | 「机器好像睡过去了，我没干完」 | 无 |
| `lock_conflict` | 「那个会话你正开着，我不敢动」 | 「关掉之后回『继续』」 |
| `credential_missing` | 「我这边的登录好像过期了」 | 「修好之后回『继续』」 |
| `cli_unavailable` | 「我这边工具起不来，先别派活」 | 「修好之后回『继续』」 |
| `error` | 「干到一半出错了：<脱敏后一句>」 | 无 |

文案只在 `bridge/worker.py`（或新的 `bridge/report.py`）里定义一次，测试逐条断言——**不许两处各写一份**。

## 7. 测试（约 14 条）

1. 成功 → 群里 `say` 行带 `parent_id=origin_mid`，正文含结论与人话、**不含禁用词**
2. 失败 → 群里有摘要 + 私聊有完整交接单（两条 `say`，uuid 不同）
3. `blocked` → 私聊里有 `open_question`，任务 `blocked`
4. **顺序**：outbox 先于 ack（用假 sender 卡住 outbox，断言事件仍 `leased`；放开后 ack 才发生）
5. **崩溃恢复**：入队后立刻 kill worker → 重领时不重复入队（按 uuid 查重）
6. 主人回「继续」→ 产生 attempt+1 的 work 事件，任务回 `running`
7. 重派 3 次 → `failed` + 群里说明
8. 六种 `kind` 的文案逐条断言（含禁用词扫描）
9. 摘要长度上限 800 字：超长截断且末尾给"完整交接单在私聊"
10. 私聊交接单按段切条（沿用 help 的分条规则，标「第 i/n 条」）
11. 群里那条与私聊那条都走 `publish_say`（出口唯一门禁 `test_single_exit` 全绿）
12. `ack_event` 对 `work` 的语义：仍只认 `leased` + claim_token，且**只有 enqueue 成功后**才 ack

## 8. 真机验收（3 分钟，要主人配合）

1. 群里 @ 机器人一件**小活**（例如「看一眼仓库里 README 的第一行，告诉我是什么」）
2. 私聊收到卡 → 引用回「做」
3. 期望：群里出现**引用原消息**的结果；`tasks.state='done'`；`events` 里 work 事件 `done`；`outbox` 两条（群/私聊）`sent`
4. 反例：把 `workbench.cli` 指向不存在的路径 → 再派一件 → 期望群里「我这边工具起不来」+ 私聊交接单 + 任务 `blocked`

## 9. 估时

**0.5–1 天**（文案与顺序判定占一半）。
