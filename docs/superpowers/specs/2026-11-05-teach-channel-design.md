# 教学通道设计：master 在私聊里把 bridge agent 带出来

- 日期：2026-11-05
- 状态：**设计稿，待批准**。未写任何实现代码。
- 相关：[CONTRACTS.md](../../../CONTRACTS.md)（消息过滤、挂起开关、外部消费者）、
  [agent_prompt.py](../../../agent_prompt.py)、[bridge/hold.py](../../../bridge/hold.py)、
  [bridge-hold-switch-requirements.md](../../bridge-hold-switch-requirements.md)（同类需求的上一个先例，可直接当模板）

---

## 1. 意图

每台部署在同事桌面上的 bridge 有一个 **master**：这台机器本机飞书账号的主人
（`config.json` 的 `target_open_id`，运行时可从飞书账号身份读到，不写死任何人名）。

master 在私聊里对它说一句话——「以后引用文件都给绝对路径」「报价的事先问我」
「内部资料在某个位置」「这条答错了，应该是……」——这句话就变成一条**教材**。
下一次它替人回答问题时，教材已经在它的 prompt 里。

目标不是「让系统从数据里自己变好」，而是**有人带它**：教材的来源只有 master 一个人，
不是统计、不是挖掘、不是模型自我反思。

**这条通道是双向的，两半同等重要**：

- **master → 它**：教原则、资料、风格、对错（§7.1–§7.7）。
- **它 → master**：拿不准、指令不清楚、可能做错时，**必须在私聊里问清楚**，而且问题要能收到回答
  （§7.8）。问完没人接，等于没问。

## 2. 现状：今天谁在学

现在的学习闭环是手工的，只发生在维护者手上：

```
同事反馈 → 人写进 docs/HISTORY.md → 人改 agent_prompt.py → 发 release → 重启消费者
```

（`_research_sentence` / `_escalation_sentence` 就是这么来的，来源见
[history §9.0](../../HISTORY.md#L342)。）

四处具体缺口：

1. **采集**：控制通道（[service.py:202](../../../bridge/service.py#L202) `control_tick` →
   [:243](../../../bridge/service.py#L243) `handle_control_message`）已经有「本人身份 + 会话白名单 +
   30s 轮询 + 游标 + message_id 去重 + 精确指令准入」一整套，但只认 `下班/上班` 两个词，
   **其余消息读完即丢、不落库、不留原文**。
2. **注入**：消费者是**一次性进程**（每条消息起一个 DSH/Codex 进程，会话不跨事件），
   prompt 全部来自代码常量。学到的东西没有地方可写，也没有通道回到 prompt。
   而且 prompt 有**六个渲染点**，不是一处：`dsh-consumer.py:366`、`codex-consumer.py:290`、
   `agentkit/driver.py:58`、完全绕开 `build_prompt` 自己拼串的内置 analyst
   （[bridge/agent.py:558](../../../bridge/agent.py#L558)），以及两个纯文本的会话式 prompt
   （`skills/feishu-bridge-consumer/SESSION-PROMPT.txt`、`...-remote/SESSION-PROMPT-WINDOWS.txt`）。
3. **投递**：事件 payload 是 bridge → 消费者的唯一数据通道，但它有**两份序列化实现**
   （[cli.py:979](../../../bridge/cli.py#L979)、[gateway.py:90](../../../bridge/gateway.py#L90)），
   连 `EVENT_KINDS` 都有两份（[store.py:29](../../../bridge/store.py#L29)、[gateway.py:34](../../../bridge/gateway.py#L34)）。
   不收敛的话，任何新字段都会变成两处行为。
4. **配置是启动快照**：`config.json` 只在启动读一次（`service.py:794` → `Service.__init__`），
   运行期唯一的活读文件是 `external.json` / `hold.json`（mtime+size 缓存）。
   所以**任何「改完立刻生效」的东西都不能放 config.json**。

## 3. 目标与判据（每条都可复跑）

1. master 在自己的私聊里 **@ 自己** 发一句「以后引用文件都给绝对路径」→ 下一次外部消费者 claim 到的
   payload 里出现该条目 → 下一次回答体现它。
   **全程不发 release、不重启 bridge、不重启消费者。**
2. 没 @ 自己、不是 master、非 p2p 私聊的话 → 零写入、零教材、不产生小心跳。
3. **回执不自激**：master 连教两条后，再跑两轮轮询，教材条目数不变
   （回执由本人账号发出、会被轮询读回，靠「教材必须 @ 本人」在结构上排除，见 §7.3）。
4. 教材文件被手工改坏 → 不注入、payload 里带显式 `error`、`status` 与 `doctor --assert` 报 fail；
   **不允许当成「没教过」静默放行**。
5. 撤回一条 → 下一次 claim 的 payload 里没有它，历史记录仍在（可追）。
6. 本地 `feishu-bridge events claim` 与 HTTP 网关 claim 两条路径的 `teachings` 字段**逐字一致**
   （同一个函数，一条断言）。
7. `external` 关闭、走内置 analyst 时，教材同样生效（两套入口对同一问题给同一个答案）。
8. 图片 / 表情 / 文件这类非文本消息**不会被吃成教材**：按 `msg_type` 闸门拒绝，并回一条说明（§7.2）。
9. 一轮轮询里消息超过一页（50 条）时**不静默丢**：窗口分页读全（§9 步骤 ⓪）。
10. **bridge 自己发出的任何消息都不会变成教材**——靠结构（教材必须 @ 本人，bridge 从不 @），
    不是靠过滤表或状态账本（§7.3）。判据是一条枚举测试：所有主动文案都不带 @。
11. 引用回复一条答复说「这条答错了，应该……」→ 教材条目带上下文（原问题 + 那条答错的答复），
    不是只有一句孤零零的评价（§7.2、§7.4）。
12. **问出去的问题回得来**：agent 在私聊里问 master，master 引用回复后，它会把答案记下、
    并回去补答原来那个人；问完就沉底不算通过（§7.8）。
13. **`know` 档的教材不会原样出现在对外回答里**：拿一条 `know` 教材去问，回答里不出现该条原文
    片段（§7.10）。

## 4. 非目标（这一版明确不做）

- **不跨机器汇总教材**。每台各学各的，同事 A 教的东西到不了同事 B 的 agent 上。
  等教材真长起来再谈分发；现在建同步机制是为一个还不存在的需求造机器。
- **不让 agent 回写教材**。三条硬理由：① Codex 的 answer schema 是
  `additionalProperties: false`（`codex-consumer.py:67-68`、`:232-233`），答复 JSON 多一个键
  直接失败；② 消费者契约明令禁止写 bridge 状态文件（CONTRACTS.md）；③ 要回写就得动答复契约
  并升版，代价远大于把教材来源限定成 master 原话。
- **不做向量检索 / RAG**。本机量级：81 条事件、10 次 DSH 运行。关键词足够，且能 diff、能回滚。
- **不做能力授权**（MCP、子代理、删除、密钥仍然硬禁）。全仓没有「能力授权」开关：
  能力是模块常量 + prompt 硬编码，要放开必须同时改 Cursor / DSH / Codex / prompt 四处
  （见 [CONTRACTS.md](../../../CONTRACTS.md) §外部消费者能力模型）。只改 prompt 就是
  「prompt 说了、沙箱没给」，正是 CONTRACTS 那一节点名不允许的。
- **不从历史数据挖学习信号**。信号源是 master，不是埋点。

## 5. 反目标（做到这些也算失败）

- 教材变成第二份 prompt：同一条规则在 `agent_prompt.py` 和教材里各写一遍 → 将来必错一处。
  分工见 §8，是硬约束。
- 教完要发版才生效 → 这条通道等于没做。
- 教材静默截断 / 静默跳过坏行 / 静默丢弃超限条目 → 违反 [AGENTS.md §1](../../../AGENTS.md)。
- 教材损坏时 fail-open 当成「没教过」 → master 以为它在照做，其实没有，比报错危险得多。
- 教材把内部数字、内部链接、对某个人的评价原样念给提问的人 → 数据安全问题，不是风格问题（§7.10）。

## 6. 约束（决定方案形状的现实条件）

| 约束 | 后果 |
|---|---|
| 消费者进程一次性，会话不跨事件 | 教材只能落文件、每次运行重新注入 |
| bridge 服务端**没有模型**（macOS 有 `cursor-agent` 子进程，WSL2 里是 exit 127 的桩） | 服务端不能「理解」一句话 → 写入环节不依赖模型（§7.4） |
| `config.json` 只在启动读 | 教学开关必须走 mtime 文件（§7.2） |
| 事件协议是跨平台契约，原生 Windows 形态 B **只能靠 payload**（没有 consumer 运行时、网关无取文件接口） | 注入必须走 claim 的 payload，不能假设消费者能读本机文件 |
| payload 无键白名单（`store.py:589-598` 只校验顶层 `{kind,dedupe_key,payload}`），但 `build_prompt` 只读固定几个键、其余静默丢弃 | 加字段安全，但必须显式渲染，否则模型根本看不到 |
| 私聊默认不采集（CONTRACTS.md §消息过滤） | 教学要单独一条显式白名单，不能顺带把 p2p 变成业务消息来源 |
| `PRAGMA user_version` 有「更高版本拒绝打开」门禁 | 教材不进 SQLite 新表：那会把 release 回滚绑死（§7.1） |
| bridge 以**本人账号**发消息，回执的 sender 就是 master | 自激回路靠**结构**堵：教材必须 @ 本人，bridge 从不 @（§7.3）。不引入标记、不引入回声账本 |
| 消费者进程一次性、会话不跨事件，事件结束后无法再续 | 问出去的问题收到回答后，只能**重放一条新事件**把答案带回去，不能"唤醒"旧进程（§7.8） |
| Codex 的答复 schema 是 `additionalProperties: false` | 问答、归纳的产物都不能塞进答复 JSON，只能走 CLI 落盘（§7.8、§7.9） |
| `chat_messages` 限 `page_size ≤ 50` 且**没有分页**；`control_tick` 只要调用成功就把游标推到 `end_ms` | 窗口里超过 50 条的部分被静默丢掉。今天丢的是 `下班/上班`（只是没人发现），加了教学就丢教材 → 必须补分页（§9 步骤 ⓪） |
| `chat_messages` 不返回 `chat_type`，无法从消息本身判断是不是 p2p | 教学会话只能在**启用时**校验一次并落盘，不能每条消息去猜（§7.2） |
| 两个 SESSION-PROMPT 是随 skill 分发的纯文本，不经过 `build_prompt` | 教材渲染点从 4 个变成 6 个；规则文本只能靠测试钉住一致（§7.6） |

## 7. 方案：分层教材 + 复用控制通道 + claim 时注入

（三种候选：A 整份准则文档 / B 条目化记忆 / C 分层。已选定 **C**，理由：原则与风格必须每次在场
且互相一致，资料只在该用时调出来；A 和 B 各自只擅长一半。）

### 7.1 教材的形态：一份追加日志，两层视图

**存储**：`home/teachings.jsonl`，一行一条不可变记录。整文件原子重写
（临时文件 + `replace`，0600），与 [hold.py:78](../../../bridge/hold.py#L78) `write_state` 同一写法——
教材体量小（上限 200 条），原子重写换来「读的人永远看到完整快照」。

**为什么是文件不是 SQLite 新表**：SQLite 有 `user_version` 门禁（`store.py:44-49`：
更高版本在任何写入前拒绝）。新表 = 升 schema = 旧 release 打开新库被拒 → **教材会把 release
回滚绑死**。而教材是数据不是代码，回滚 release 不该影响 master 教过什么；教材文件坏了也只影响
教学、不影响接待。两条都指向独立文件。

**记录**（不可变，只追加）：

```json
{"v":1,"rev":12,"op":"add","id":"t-0007","kind":"principle","expose":"say",
 "text":"引用文件时给绝对路径","at_ms":1793790000000,
 "chat_id":"oc_xxx","message_id":"om_xxx","reply_to":"om_yyy|null","by":"master"}
```

`expose` 只有两档，管的是「这条能不能原样说给提问的人听」：

| 档 | 意思 | 默认给谁 |
|---|---|---|
| `say` | 可以直接用，也可以说出来 | 原则、风格、对错反馈（`principle`/`style`/`feedback`） |
| `know` | 可以用它判断，但**不许原样说出**（不念原文、不贴链接、不复述数字） | 事实与资料位置（`fact`/`pointer`） |

两档都进 prompt，但**分开标注**，模型看得见哪条属于哪档（§7.10、§8 第 5 条）。master 可以当场
覆盖：说「这条可以对外说」/「这条别对外说」。回执每次都报这条落在哪档，你说错了一句就能纠。

- `op` ∈ `add` / `disable`。撤回 = 追加 `disable`，**不做 in-place 修改**，
  和 releases「不可变副本」同一思路。
- 按 `message_id` 幂等：同一条飞书消息重复投递（重启、游标回退、5 分钟回看）不得重复写入。
- 当前状态 = 重放日志得到 `{"rev":N,"charter":[...],"notes":[...],"error":null}`。
  **坏行不参与重放，但要计数并在 `error` 里写明「有 N 行读不出来」**（不静默）。

**引用回复要带上上下文**：master 引用回复 bridge 的某条答复、说「这条答错了，应该……」时，
`reply_to` 指向那条答复的 message_id（`outbox` 里存着 `reply_id`，`store.outbox_sent(...)`）。
落库时把它解析成 `ref: {question: 原消息正文截断, wrong_answer: 那条答复截断}`，注入时跟着条目
一起给模型——只给一句「这条答错了」而不知道「这条」是哪条，等于没教。
解析不到（引用的是更早的、已被 prune 的消息）就写 `ref: null`，并在回执里明说
「我没找到你引用的那条，只记下了你的话」，不静默降级成普通教材。

**两层视图**（对应 C）：

| 层 | `kind` | 注入策略 | 装什么 |
|---|---|---|---|
| 准则 charter | `principle` / `style` / `feedback` | 整份注入 | 做事原则、语言风格、哪次对了/错了 |
| 资料 notes | `fact` / `pointer` | 按需注入 | 读到过的事实、该去读的资料位置 |

**上限**（写入时拒绝，不是注入时截断）：单条 ≤ 500 字；启用条目 ≤ 200 条；注入总量 ≤ 4000 字。

> 我的判断：v1 两层**在预算内就全注入**，超出预算才启用「按会话 / 标签关键词取前 N 条」。
> 结构是 C，但不为一个还不存在的规模先建检索机制。可推翻（§11 第 1 条）。

### 7.2 通道：复用控制轮询，不新增事件类型

**采集**挂在既有控制通道上：`is_control_message` 为假、且满足三条前置的消息 → 教学消息。

前置（缺一不可）。**判定顺序很重要**：先看 `parent_id` 是不是命中「正在等回答的问题」
（§7.8），是就当答案处理——**这一步不要求 @**；不是才按下面四条判教材。

1. `sender.id == config['target_open_id']` —— master 本人；
2. `chat_id` 是**本人与自己的 p2p 私聊**（启用时校验一次并落盘，见下）；
3. **消息 @ 了本人自己**（`mentioned(message, target_open_id)`）——这是整条通道的**结构地基**，
   不是多余的门槛：bridge 自己发出的消息从不带 @，所以「我的回执被读回来当教材」在结构上不可能，
   不需要标记、不需要账本（§7.3）；
4. 不是精确指令（`教材清单` / `忘掉…` 之外的都算教材）、`msg_type ∈ {text, post}`；
   且 `create_ms ≥ enabled_at_ms`。

第 4 条里的 `msg_type` 闸门不能省：**「正文非空」当不了判据**——`message_text` 对图片/表情/文件
返回的是 `[图片，尚未读取像素]` 这类占位串（[transport.py:49-56](../../../bridge/transport.py#L49-L56)），
永远不空。非文本类型回一条「这个类型我读不了，换成文字」再丢弃，否则教材里会攒满占位符，
而这些东西会出现在每一次运行里。

**为什么限定 p2p**：`chat_messages` 不返回会话类型，所以校验只能在启用时做一次——
`feishu-bridge teach enable --chat oc_xxx` 调会话信息接口确认 p2p，不是就**拒绝启用**。
群里教有两个问题：master @ 自己的每句话会被群里所有人看见，而教材内容（内部资料位置、对谁的评价）
本来只该在私聊里存在。

**依赖分页**：`chat_messages` 只取一页（`page_size ≤ 50`）而 `control_tick` 只要调用成功就把
游标推到 `end_ms`（[service.py:230-231](../../../bridge/service.py#L230-L231)）——窗口里超过
50 条的部分今天就在被静默丢掉（丢的是 `下班/上班`，只是没人发现）。教学上线前必须先补分页，
见 §9 步骤 ⓪；否则丢的是 master 教的东西，而 §5 明令不允许静默丢。

**开关与那个私聊放 `home/teach.json`（mtime+size 缓存读），不放 `config.json`**：

```json
{"schema":1,"enabled":true,"enabled_at_ms":1793790000000,"chat_id":"oc_xxx",
 "max_entries":200,"max_item_chars":500,"max_inject_chars":4000}
```

理由见 §6（config 是启动快照，闭包会砸掉判据 1）。写法照 `external.json`（`service.py:279`）。

`chat_id` 是**单个**会话，不是列表：每个人只有一个自己 @ 自己的私聊，多个入口没有语义。
由 `feishu-bridge teach enable --chat oc_xxx` 写入，写入前先校验 p2p（§7.2）。

**为什么不用 `self_chat_ids`**：它的语义是「这个会话里本人发的话可以当控制指令」，
而且不要求 @——留着是为了让下班开关好按。教材要求 @ 且必须是 p2p，两者判据不同；
复用同一个键会让「哪天为了下班开关把群加进 `self_chat_ids`」变成「群里的话都进教材」。
两个语义两个键。

**为什么不新增事件 kind（`teach`）** —— 勘察结果是 12 处会受影响，逐条都得判断：

| 位置 | 会怎样 |
|---|---|
| `store.EVENT_KINDS` + `_validate_event` | 新 kind 被拒，必须加白 |
| `gateway.EVENT_KINDS`（复制的第二份） | 同上，两份必须同改 |
| `ack_event` 只接受 `attention` | 新 kind 能领不能 ack |
| `complete_external_reply` 只接受 `message` | 新 kind 不能 reply |
| `expire_external` / `rollback_external` 只扫 `message` | 新 kind 永不超时、永不回滚 |
| `prune_expired` 只删 dead/done | 新 kind 永久 pending |
| `drop_pending` 用 `kind<>'message'` 分口径 | 挂起计数语义被改写 |
| `emit_attention_events` 只有 attention 生产者 | 缺生产者路径 |
| CLI `events claim --kind` choices / `events reply` | 硬编码 |
| `consumer_runtime` 只认 message | 远端消费者看不到，叠加前一条 = 永久积压 |
| CONTRACTS / CONSUMER-TEMPLATE / consumer skill | 文档按两种写 |

而这些代价换来的东西（「进队列」）这一版根本不需要——教学**不依赖模型**就能落地（§7.4）。
所以：不进事件系统，复用轮询骨架。

**挂起期间照常接收**：挂起只关业务接待，不关 master 的指令通道（否则下班后没法教它，
而「夜里教」正是这功能最自然的使用场景）。与现有 `下班/上班` 同一条通道、同一个豁免。

### 7.3 自激回路：用 @ 堵死，不留第二套机制

bridge 是**以本人账号**发消息的：回执的 `sender.id` 就是 `target_open_id`，会话就是那个私聊。
hold 通道侥幸免疫（`command_for` 只认两个精确词，回执文案匹配不上）；教材接受任意文本，
所以「回执下一轮被读回来当教材 → 又产生回执」是真实风险。而且同一会话里不止回执一个来源：
`ask_owner` 求助、漏答提醒、§7.8 的回答回执，都发到这个私聊。

两条候选：

- **状态方案**（记住发过哪些 `message_id`）——否掉。任何账本都有崩溃窗口：发出去了、还没记账
  就重启 → 回执被读成教材 → 又产生新回执 → 循环放大。要盖住重启后 5 分钟回看（`service.py:216`）
  和 `notify` 那个**独立进程**，账本还得跨进程共享，复杂度不成比例。
- **结构方案**（教材必须 @ 本人）——采用。`transport.send_text` / `reply` 永远不带 @，
  而飞书消息的 `mentions` 由客户端产生，所以「bridge 自己发的消息满足前置条件」在结构上不可能。
  一处判据、零状态。

代价是 master 每教一句要多 @ 自己一次。这是**明确接受**的代价：换来的是「永远不会自己教自己」
这条不变量，而不是「通常不会」。另一个选项（给 bridge 的每条通知加固定标记）被否掉——
那要靠约定（每条新通知都记得加标记），约定会漏；@ 靠的是别人做不到，不会漏。

**推论（必须写成测试）**：bridge 主动发出的每一条文案——教材回执、挂起/恢复回执、`ask_owner`
求助、漏答提醒、问答回路回执——**一律不许 @ 本人**。谁哪天为了「提醒更醒目」给回执加个 @，
整条通道当场变成自激回路。判据：一条枚举测试遍历所有主动文案的渲染函数，断言
`mentions` 为空、正文里不出现 @ 提及实体（§3.10）。

**重启与回看**仍然需要下界：`enabled_at_ms` 写进 `teach.json`，把启用之前的历史 @自己 消息
挡在外面；`message_id` 幂等（§7.1）保证重复投递不会写两遍。

### 7.4 写入不需要模型（这一版的关键取舍）

**教材就是 master 的原话，不转述、不归纳、不改写。**

- 服务端没有模型（§6），让服务端「理解」一句话不可行；
- 原话入库 = 零失真、可审阅、可撤回。让模型归纳会引入「教了个寂寞」的失真
  （「引用文件都给路径」被归纳成「强调路径」，行为就变了）；
- 注入时模型本来就在场，**理解发生在它读教材的那一刻**，不需要提前做掉。

**回执**由服务端直接发（模板文案，不需要模型），复用控制回执那条 `transport.reply`
路径（`service.py:265`）：

```
记下了（第 12 条 · 原则 · 可以直接说）：引用文件时给绝对路径
· 说「教材清单」看全部；说「忘掉最后一条」撤回
· 教材只影响做法与偏好，不改变权限（删除/密钥/MCP 仍然禁止）
```

前两行随内容变，最后一行**固定、每次必带**：它是「能力授权不在这一版」的可见契约——
不靠隐藏逻辑，靠明说。条目标题里的「可以直接说 / 只能自己知道」就是 `expose` 档位（§7.1）：
默认 `fact`/`pointer` 落「只能自己知道」，你说一句「这条别对外说」就换档。

合并回执：一轮轮询里同一会话的多条教材合并成一条回执（「记下了 3 条：…」），
不需要额外状态，`control_tick` 本来就是按批处理。

### 7.5 撤回与查看：两个入口，一份事实

- **飞书侧**（人在手机上）：精确指令，与 `下班/上班` 同级、同样精确匹配、不做模糊：
  `教材清单` / `忘掉最后一条` / `忘掉 t-0007`。清单最多回 20 条（消息长度）。
- **CLI 侧**（人在电脑上）：`feishu-bridge teach list|show <id>|revert <id>|disable|enable|status`。
  `cli.py` 不是真子命令结构：顶层 `command` 是 choices 白名单（`cli.py:1256`）+ if 链分发
  （`:1262-1298`），`teach` 按 `_hold` 的形状加（自建 parser + `_cli_lock` + 原子写）。

两个入口写同一份日志、走同一个重放函数——「一条事实一个答案」的落实。

**两个写者必须真的串行化**：`hold.write_state` 那句「CLI 与服务都可能写，最后一次 replace
生效」对**快照**成立，对**追加日志**是丢数据（服务正在 `add`、CLI 同时 `revert`，谁后写谁
抹掉对方）。所以 `home/teach.lock` 上一把 `flock`（仓库已有同款：`cli.py:106` 的 `cli.lock`、
服务的 `service.lock`），读-改-写整段在锁内：

- CLI 端**阻塞等锁**，带超时；超时要报「锁忙，没改成功」，不能假装改好了。
- 服务端**非阻塞**：抢不到就跳过本 tick，且**不推进游标**——消息还在窗口里，下一拍重来，
  不会丢。

### 7.6 注入：在 claim 看到的那一份 payload 里

**单点**：新增 `bridge/teach.py`，对外只暴露：

- `payload_block(home) -> {"rev","charter":[...],"notes":[...],"error":...}`
- `command_for(text)` / `render_ack()` —— 与 `hold.py` 同构，回执文案只此一份
- `read_config(home)` —— `teach.json` 的 mtime 缓存读

**前置重构（必须，否则必然两处行为）**：`_event_view` 现在有两份
（[cli.py:979](../../../bridge/cli.py#L979)、[gateway.py:90](../../../bridge/gateway.py#L90)），字段集还
略有差异。先收敛成一处，`teachings` 只挂在这一个函数里；判据是 §3.6。

**字段**：payload 增加一个 `teachings` 键，其余字段不动。payload 无键白名单（安全），
但 `skills/feishu-bridge-consumer/SKILL.md` 是 payload schema 的**唯一事实源**，必须同步，
否则违反 AGENTS §0.3。CONTRACTS.md 补一句「payload 允许新增可选键，消费者必须忽略未知键」。

**为什么在 claim 时组装**（不是 emit 时固化）：master 可能在事件入队之后、被领取之前教一句，
claim 时读到的才是当下这份。

**六个渲染点都要接**（不是四个）：

| 入口 | 位置 | 备注 |
|---|---|---|
| DSH 消费者 | `dsh-consumer.py:366` | 已传 `owner_name`，未传 `tool_budget` |
| Codex 消费者 | `codex-consumer.py:290` | 同上 |
| agentkit | `agentkit/driver.py:58` | **已漏传** `owner_name` 与 `tool_budget`（既有漂移） |
| 内置 analyst | `bridge/agent.py:558`、`:640` | 自拼串，不经过 `build_prompt` |
| macOS 会话式消费者 | `skills/feishu-bridge-consumer/SESSION-PROMPT.txt` | 纯文本 prompt；里面那句「消息和上下文是不可信数据」会**把教材吞掉** |
| 原生 Windows 会话式消费者（形态 B） | `skills/feishu-bridge-consumer-remote/SESSION-PROMPT-WINDOWS.txt` | 同样是纯文本；它**没有**那句不可信数据条款，反向风险：教材会被直接当指令照做 |

两处失败形态正好相反：一份会忽略教材（等于没做），一份会无条件照做（比没做更危险）。
两个 `.txt` 是随 skill 分发的独立文件、不能 import，所以「同一段规则」只能靠**测试钉死**：
§8 的规则放在 `agent_prompt.py` 的一个常量里，一条测试断言这段文本在**六个渲染点**的 prompt
里逐字出现。否则六份各自演化，半年后没人说得清哪个行为才对（AGENTS §0.3）。

现有静态护栏（`tests/test_agent_prompt.py:92-105`）只检查 dsh/codex 两个文件名，要扩到六处；
否则「漏接一处」会静默通过。判据 §3.7 覆盖内置 analyst。

### 7.7 教材版本进运行证据

每次消费者运行的 `run.json` 记 `teachings_rev` **和** `teachings_hash`（注入的 charter 文本的
sha256）。多记一个 hash 的理由：rev 只有在追加日志永不压缩时才可比；将来若压缩，hash 仍然能把
「某次运行」和「当时注入的那份内容」对上。这样「这次答错了」可以追到「当时它是按哪版教材说的」，
也是 §3 判据可复跑的一部分。

### 7.8 问答回路：它问你，你答它（「问清楚」那一半）

master 的要求是硬的：**有疑虑、拿不准、指令不清楚，必须在私聊里问清楚**。现状是问得出去、
回不来——`ask_owner` 能把问题私聊发给本人（`notify`：6 小时去重、每小时 6 条上限），
但 master 回了之后**没有任何东西接住**，事件早已终态，那句话说给空气。

更要紧的是：**那句"回我一句就行"已经写在文案里了**（[consumer_runtime.py:228](../../../consumer_runtime.py#L228)：
「直接回我一句就行，我照你说的处理；也可以直接回那条消息」），只是没人实现它。
所以这不是加功能，是**补上一个已经承诺过的回路**。

设计四件事：

1. **问题登记**：消费者提交 `ask_owner` 时，bridge 往 `home/questions.jsonl` 追加
   `{id, at_ms, event_id, consumer, question, needs, dm_message_id}`（与教材同一套原子写 + flock）。
   `dm_message_id` 是那条 DM 的 id，它是**回来的钥匙**。
2. **回来的路**：master 在私聊里**引用回复那条 DM** 写答案。轮询拿 `parent_id` 对上
   `dm_message_id`，然后做三件事。**这条路不要求 @**——引用回复本身就是结构判据
   （bridge 从不引用回复自己的通知），要求 @ 反而会让人答不进来：
   答案落成教材（`needs=fact→fact`、`decision→feedback`、`access→principle`，
   带 `ref` 指向问题与事件）；回一条回执；**重放一条 message 事件**把答案带回给原来提问的人——
   `dedupe_key=followup:<原 mid>:<问题 id>`、payload 多一个 `owner_answer`。
   消费者把它当普通消息处理，回答时带上 master 的决定。
3. **不猜**：没引用回复、且**同时有多条待答**时，回执只说「现在有 2 个问题在等你，引用回复
   其中一条」，不猜是哪条；只有恰好一条待答时才接受不带引用的回答。
4. **不重复**：同一问题 id 只认第一次回答；之后的当普通教材，回执里说明。

代价与取舍：

- 新增一个状态文件与过期策略（已回答保留 30 天）。
- 后续跑是一条**新的 message 事件**，会吃掉一次回复配额（`app_daily_reply_cap` 默认 20 条/天），
  要在配额里算进去，不能悄悄饿死正常答复。
- master 的答案本身可能错/过期 → 会照着答错一次。可撤回，但错的话已经发出去了。
- 被否掉的方案：**唤醒原来那个进程**。会话不跨事件、进程可能已经死了、租约也要续，
  比「重放一条事件」复杂得多，而且失败时没有退路。重放天然幂等，也天然可审计。

### 7.9 归纳层：复杂度、可行性、可靠性（你要的评估）

结论先说：**归纳层不是一个功能，是两块难度差一个量级的东西**，必须拆开做。

**⑤a 机械归并（不碰模型）**

| 维度 | 评估 |
|---|---|
| 做什么 | 按 `kind` 分组；去掉完全重复的；把同一天连续的同类条目并成一条；超长条目按句切分并提示；给每条稳定的短 id |
| 复杂度 | **小**：纯函数 + 现有日志，半天量级 |
| 可行性 | **确定**，不改写一个字，所以不可能失真 |
| 可靠性 | **高**：可断言「归并前后 master 能看到的实质内容不变，只是组织方式变了」 |
| 解决什么 | 「条目多了看不过来」的一半：重复与碎片 |

**⑤b 模型归纳（真正的重写）**

| 维度 | 评估 |
|---|---|
| 做什么 | 把 N 条原话压成 M 条准则（M<N），合并同义、发现冲突、删过期 |
| 复杂度 | **大**，而且大在不是代码的三处（下详） |
| 可行性 | 可行，没有捷径 |
| 可靠性 | **取决于确认环节**；模型自身的可靠性不可控 |

复杂度落在三处：

1. **模型在哪跑**。只有消费者有模型。做法：master 说「整理一下」→ `teach.json` 置
   `pending_induction` → 下一次 claim 时消费者**先**跑一趟无工具、短超时的归纳
   （「超时第二趟」在 [bridge/agent.py](../../../bridge/agent.py) 已有先例），把候选写进
   `teachings.candidate.jsonl`，**再**正常回答业务消息。不新增事件类型，不碰答复 JSON
   （Codex 的 `additionalProperties: false` 挡着）。
2. **失真**。对抗办法只有一条硬的：**每条候选准则必须带来源 id 列表**
   （`from: ["t-0007","t-0012"]`），并且必须交代每个来源的去向（merge / keep / drop+理由）。
   做不到就不许替换。这是判据，不是善意。
3. **确认**。候选**不自动生效**：master 在私聊里看到 diff（「8 条 → 5 条：合并 2 组、
   删 1 条过期、2 条冲突等你选」），回「确认」才替换；原话条目**不删除**，只标 `superseded`，
   随时可整体回退。

**我否掉的版本：自动生效。** 一旦自动生效，错的规则会以本人身份说出去，而「它什么时候偷偷
改了自己的准则」是不可审计的——这条风险比归纳本身值钱。

**建议顺序**：①–④ 跑通、攒到 20~30 条真实教材之后再上 ⑤b；⑤a 到 50 条左右就该做，
⑤b 的触发点是 100 条或第一次出现准则冲突。**先有内容，再谈整理**——现在做归纳，归的是空气。

### 7.10 数据安全：教材会不会泄出去

这一节不是免责声明，是把四条真实路径摆出来，每条配一个能查的动作。

**① 教材会离开这台机器。** 教材每次运行都进 prompt，而 prompt 会发给模型服务商——
和消息正文一样的去向。所以：教材里不写密钥/密码（本来就禁止），也不写「不该给供应商看」的东西。
想让它掌握一份内部资料，教**去哪读**，不要教**内容是什么**。这条比任何过滤都管用。

**② 对外说漏。** 同一个 AI 用同一份 payload 回答同事和回答别人，教材里的内部数字、内部链接、
对某个人的评价，都可能被当成「我知道的事」说出去。挡法就是 `expose` 两档（§7.1）：
`know` 档的条目进 prompt 时明确标注「据此判断，不许原样说出」，§8 第 5 条是它的强制条款。
判据：拿一条 `know` 教材去问，回答里不得出现该条原文片段（可复跑的断言，不是"看着像没说"）。

**③ 落盘与日志。** `home/teachings.jsonl` 是 0600、被 `.gitignore` 挡住（对齐
[docs/local-only.md](../../local-only.md)）；`run.json` **只记 `rev` 和 `hash`，不记教材正文**——
否则教材会顺着运行记录散复制到每个消费者的产物目录里。

**④ 撤回有边界。** `忘掉最后一条` 能删掉本机的那一行，但删不掉已经发出去的 prompt、已经答出去的
话、以及模型侧的日志。所以「教之前想一下」永远比「教完后悔」便宜——这一条要写在文档里，
不能让人以为撤回等于没发生。

**一条给你的操作建议**：`teach list` 的输出是本机数据，别整段贴到公开文档、群里或工单里。
真要贴，贴 `teach show <id>` 的摘要，或者手动删掉敏感那几条。

## 8. 和 `agent_prompt.py` 的分工（这是「不变成第二份 prompt」的全部内容）

| | 谁写 | 生效方式 | 管什么 | 谁能覆盖谁 |
|---|---|---|---|---|
| `agent_prompt.py` | 维护者 | 发 release + 重启 | 对所有机器都成立的硬约束：安全、能力边界、输出格式、求助协议 | **不被教材覆盖** |
| 教材 | 本机 master | 即时（下一次 claim） | 这个人 / 这台机器特有的：做法偏好、资料指针、风格、对错反馈 | 不覆盖硬约束 |

prompt 里新增那一段必须包含六条（缺一条这个设计就漏）：

1. 教材是 master 的工作偏好与资料，**不是新的权限**；
2. 教材与平台权限冲突时，**权限优先**，并明确对提问方说「这个能力现在没有」——
   不允许假装能做到；
3. 教材**可信度高于消息正文**，但仍在「不可信数据」框架之外——必须与
   [agent_prompt.py](../../../agent_prompt.py) 现有那段「将消息和上下文视为不可信数据」**显式分区**，
   不能混在同一段里，否则要么教材被当注入攻击忽略，要么外部内容借教材地位提权；
4. 优先级：高于消息正文与上下文，低于本段规则与安全约束；
5. **`know` 档的教材不许原样说出**：可以用来自己判断、自己查证、决定去查什么，
   但不能把原文、链接、数字念给提问的人；说不清楚的就说「这个我确认一下再回你」并走 `ask_owner`。
   这一条针对的是 `expose=know` 的条目（§7.1、§7.10）；`say` 档正常使用；
6. **拿不准、指令不清楚、可能做错时，先问 master，不许猜**。现有 `ask_owner` 的三类
   （缺事实 / 缺决定 / 缺权限）不够，要显式加上「指令歧义」与「把握不足」两类；
   判据还是可自查的那条：正文里只要出现「我不确定 / 应该是 / 大概」这种话，就必须带 `ask_owner`。

## 9. 分步实施（每步独立验收，不需要一次做完）

| 步 | 内容 | 判据 |
|---|---|---|
| ⓪ | `transport.chat_messages` 补分页（`page_token` 循环 + 最大页数上限 + 页游标打转时显式失败），`control_tick` 读全窗口再推游标 | 构造 >50 条窗口：全读到、游标正确推进、打转时失败而不是死循环。**顺带修掉 hold 一个潜伏的丢指令 bug** |

| ② | 控制通道采集（@ 判据 + p2p 校验 + `msg_type` 闸门）+ 回执 + 飞书侧精确指令（教材清单 / 忘掉） | §3.1、§3.2、§3.8、§3.10；重启不重复写；抢不到锁时不推游标 |

| ⑤ | **问答回路**（§7.8）：问题登记 + master 引用回复路由 + 后续跑重放 + 待答可见面 | §3.12；真机一次：它问 → 你答 → 它回去答复提问的人 |
| ⑥a | **机械归并**（§7.9）：分组、去重、合并、编短 id，不碰模型 | 归并前后 master 可见内容不变；可整体回退 |
| ⑥b | **模型归纳**（§7.9）：候选 + 来源 id + 去向交代 + master 确认才替换 | 每条候选都能追到来源；确认前不生效；原话只标 `superseded`，可整体回退 |

步骤 ⑥b 的启动前提写在 §7.9 末尾：**先有 20~30 条真实教材再谈归纳**。

## 10. 风险与代价

- **context 挤占**：教材会占 prompt 预算（`agent_timeout` 480s、工具预算 12 次是硬指标）。
  4000 字是初值，真机按「回答质量不掉」校准一次；超了就收紧，不要偷偷截断。
- **教错会外溢**：它以「本人 AI 助手」的身份对外说话，一条错规则会重复很多遍。
  兜底 = 回执可见 + 可撤回 + `teachings_rev` 进证据。
- **教材 vs release 打架**：master 教了「先问本人」，新 release 的 prompt 说「先查证」。
  两者不是同一层，但**表述冲突时按 §8 的优先级表裁决**，并写进新段落，否则将来没人说得清。
- **会话选错**：`teach enable` 只接受 p2p 私聊；若将来有人强行改 `teach.json` 指到群，
  群里 master 的 @自己 消息会进教材。兜底 = 启用时校验 + 回执可见 + 可撤回。
- **回执可能吵**：v1 只做「一轮合并」，不做每小时上限；master 自己刷屏时 `notify` 那套
  限流语义不适用（那是给 agent 主动推送用的）。
- **一次性决定会被当成通用准则**：master 在 DM 里回 `ask_owner` 的那句话（「这次就先答应他」）
  会落成教材，下次被当成原则复用。这一版不动它：回执里明说「已记成通用做法，只是一次性决定就说
  『忘掉最后一条』」。要根治得让教材条目带「适用一次 / 长期」的区分，属归纳层的活（§9 第 ⑤ 步）。
- **N 台机器各学各的**：明确非目标，但每条记录带 `chat_id` / `message_id`，将来要导出有路。
- **「群里的教学」不做**：p2p 校验会挡掉群会话。若将来真要在群里教，就必须重新回答「哪句话是我
  在教、哪句话是我在答同事」——那是另一个设计，不要顺手放开。
- **分页引入新的失败面**：页游标打转、翻页语义变化、单次 tick 变慢。所以它单列成步骤 ⓪，
  有自己的超时与最大页数上限，不和教学模式混在一起改。
- **问答回路会多花一次回复配额**：后续跑是一条新事件，要算进 `app_daily_reply_cap`（默认 20 条/天）；
  配额紧张时先保正常答复，后续跑宁可排队晚一点，不能悄悄把它饿死。
- **master 不答**：问题会长期挂着。待答数进 `status`，超过 24 小时 `doctor` 报 warn（不报 fail——
  人可能就是不打算答）。答了才会清。
- **master 答错**：错误会被当准则复用，而且已经照着答过一次。可撤回，但发出去的话收不回——
  这是"问清楚"策略的固有代价，只能靠回执可见 + 撤回。

## 11. 我替你做的判断（都可以推翻）

1. **v1 两层都全量注入**，超出预算才启用关键词召回 —— 不先建检索。
2. **回执每次都发**，带固定的「教材不改变权限」尾注 —— 用可见文案代替隐藏逻辑。
3. **教材不进 SQLite**，用独立 jsonl —— 不让教材把 release 回滚绑死。
4. **教材只由 master 产生，agent 不回写** —— 见 §4 的三条硬理由。
5. **教学通道不新增事件 kind** —— 12 处受影响的清单在 §7.2。
6. **开关放 `home/teach.json` 而不是 `config.json`** —— 否则「不重启就生效」做不到。
7. **内置 analyst 也要接教材** —— 它是 macOS 兜底路径，不接就是两套语义。
8. **自激回路用 @ 堵，不引入标记、不引入回声账本** —— 结构性的不变量胜过约定和状态（§7.3）。
9. **教学会话必须是 p2p，启用时校验** —— 群会话会让「答复同事」和「教它」混在一起（§7.2）。
10. **消息类型只放 `text` / `post`** —— 「正文非空」是假的，占位串永远不空（§7.2）。
11. **先修分页再做教学**（步骤 ⓪）—— 50 条截断今天就存在，只是丢的东西没人发现。
12. **两个写者用 `flock` 串行化**，服务端抢不到锁就跳过本 tick 且不推游标（§7.5）。
13. **追加日志 v1 不压缩**；追溯同时记 `rev` 和 `hash`，将来压缩也不会断（§7.7）。
14. **两个 SESSION-PROMPT 也算渲染点** —— 否则会话式消费者（含原生 Windows 形态 B）
    静默不生效；代价是规则文本要靠测试钉住六处一致（§7.6）。
15. **问答的后续靠「重放一条新事件」，不唤醒旧进程** —— 消费者一次性、旧进程可能已死，
    重放天然幂等可审计（§7.8）。
16. **归纳层拆成机械归并（⑤a）与模型归纳（⑤b），且 ⑤b 的候选不自动生效** ——
    自动生效等于让不可审计的规则改写发生（§7.9）。
17. **教材条目分 `say` / `know` 两档（数据安全）** —— 事实与资料位置默认不许原样说出；
    两档都进 prompt 但分开标注，回执显示档位（§7.1、§7.10）。

## 12. 已确认的决定（2026-11-05，master 本人）

1. **教学界面**：自己 @ 自己私聊。→ 前置条件按 §7.2 写死为「p2p 私聊 + @ 本人」；
   安装器不必再问会话，`teach enable` 时校验 p2p 即可。
2. **对错反馈必须引用回复**，把答错的那条带过来才有上下文。→ §7.1 的 `ref` 解析是硬需求，
   §9 步骤 ③ 里有了它才算完。
3. **归纳层要做**。→ 拆成 ⑤a 机械归并（先做）与 ⑤b 模型归纳（攒到 20~30 条再做），
   复杂度/可行性/可靠性评估见 §7.9；⑤b **不自动生效**。
4. **拿不准、指令不清楚、可能做错，必须问 master。**→ 这是通道的另一半，§7.8 问答回路 +
   §8 第 6 条。判据：问得出去，也回得来。

### 12.1 数据安全的默认（我定的，可推翻）

教材里的事实与资料位置默认 **`know` 档**——它能据此判断和查证，但不会把原文、链接、数字
念给提问的人；原则、风格、对错反馈默认 `say` 档。理由与四条泄漏路径见 §7.10。

三种情况下你要推翻这个默认：
- 你希望它**敢直接引用内部数据**回答同事（更快，但等于允许它把内部数字说给任何 @ 它的人）；
- 有些教材你希望**连"知道"都不该让它知道**（那就别教，教材会进 prompt、发给模型服务商）；
- 以后接入权限体系，能按提问人身份决定说不说——那是另一个设计，现在没有这个信息。

## 12. 实施结果与设计稿的差异（2026-11-05 实施后回填）

实施严格按本稿与 [plan](../plans/2026-11-05-teach-channel-plan.md) 的 T1–T8 走，下面五处与稿子不同，
都是实施中发现的（不是临时凑合）：

1. **新增 `consumer_safety._exceeds_nesting()`（§7.3 之外）**：整包测试偶发 `Abort trap: 6`，
   根因是 `json.loads` 对 5000 层嵌套回复会打爆 C 栈、Python 只能 abort。改在交给解析器**之前**
   用迭代扫描按形状拒绝（上限 64 层），fail-closed。这是 §7.3「答复解析不能崩」的硬前提，
   已写进 `docs/HISTORY.md` §10.1。
2. **`ask_owner.needs` 从三类扩到五类**（`fact/decision/access/ambiguity/uncertainty`）：
   本稿 §8 第 6 条已经承诺「拿不准就问」，校验层不认这两个值就等于没承诺，所以随 T6 一起落地。
3. **不新增事件类型、不新增 `teach questions` 子命令**：待答数并进 `teach status` 的
   `pending_questions`；重放沿用 `message` 事件 + `payload.owner_answer`，Codex 的
   `additionalProperties:false` 一个字节没动。
4. **`teach tidy` 的"合并"= 原文按行拼接**：合并后的正文是原条目逐字相加（`ref.from` 记来源 id），
   所以「归并前后可读内容不变」是可断言的；超过 500 字或已由 tidy 合成的条目不参与合并，
   避免反复套娃。
5. **`teach show` 覆盖历史条目**：被 `supersede`/`disable` 的条目仍可查（回退的依据），
   `bridge/teach.py::find_entry` 是唯一入口。

未做（按本稿的到期条件保留，不是遗漏）：⑤b 模型归纳（等 20–30 条真实教材再开，需要自己的计划）、
④ 真机闭环（要发布新 release 且**必须本人**在私聊 @ 自己教第一句，命令与判据见
`docs/HISTORY.md` §10.2，任务板 task-9）。
