# 设计稿：L3 感知延迟（2026-11-05）

> 本稿只写设计，不改代码。上一轮我说"L3 = 内置分析器"，**实测数据把这个顺序否掉了**。
> 这份稿的第一件事是把"到底慢在哪"量出来，然后按数据排序做哪几件。

## 0. 一句话

**它现在不缺"判该不该回"的能力（通道已经在挡），缺的是"看起来像在回话"的延迟**：
一条消息从发出到飞书里看到答复，p50 约 50 秒（最近 8 条 31～95 秒），其中**采集占一半**、
模型单轮 7～12 秒、投递 4～6 秒。所以 L3 先做可观测 + 采集提速，回执要不要做由 T1 的数据决定。

## 1. 现状证据（2026-11-05 20:30，本机生产库只读查询）

一条消息的生命周期，按 `inbox.create_ms` / `inbox.received_at` / `outbox.created_at` / `outbox.verified_at` 四列拆开：

| 段 | 含义 | 全量 108 条 p50 | 最近 8 条 | 谁能压 |
|---|---|---|---|---|
| ① | 飞书里发出 → bridge 采集到 | 20s（p90 35s） | **11～44s，p50 27s** | 采集间隔（配置） |
| ② | 采集到 → 答复已生成 | 73s（p90 203s） | **12～29s，p50 13s** | 模型单轮 / 消费者管道 |
| ③ | 生成 → 飞书读回确认 | 5s（p90 6s） | 4～6s | 已经很稳，不动 |
| 合计 | 发出 → 飞书里看得见 | 99s | 31～95s，p50 ≈ 53s | — |

三处细节：

1. **采集就是 12 秒一次的轮询**：`config.json: live_interval_seconds=12`，日志里实测相邻 `search live`
   间隔 p50 = 14s（12s 间隔 + 单次扫描约 2s）。也就是说，一条消息平均要等半个间隔才被发现，
   这 6～7 秒是**纯等待**，不是处理。
2. **模型单轮没有想象中慢**：`consumer-agent-runs/dsh/run-*/run.json` 里 `duration_seconds` 最近三条
   6.6s / 8.5s / 11.5s（0 次工具调用）；带工具的那批历史样本 p50 21s、p90 72s。
   全量 ② 的 p90 203s 是被历史（旧代码、重试、多人同时问）拉高的，**不该拿它当现状**。
3. **通道判定已经在挡不该起模型的消息**：`inbox` 156 条里 33 条 `ignored`
   （15 条没 @ 我、6 条教材私聊、3 条自己的、9 条人工），129 条里 107 条已答完。
   **也就是说"该不该回"这件事今天已经由 admission 规则回答了。**

## 2. 为什么不做「内置分析器」（先把结论说清）

原本的设想是：在 bridge 里加一层本地分析器，判"要不要回 / 该谁办 / 现在回不回"，省掉不必要的模型调用。

数据不支持，三条理由：

1. **省不出延迟**。延迟的大头是采集 27s + 模型 12s；"这条不用模型"能省的只有模型那 12s，
   而且省掉的那条本来也不需要回复——用户感知不到"变快"，只感知到"更少乱回"。
2. **判定已经存在**。admission（`mentioned()` / `own_message` / `teach_channel` / 自聊白名单）在做同一件事；
   再加一套"分析器判定"就是**同一个事实两个答案**——AGENTS §0.3 明令禁止的那条。
   真要加，只能是"把现有 admission 的输出暴露出来"，不是再造一层。
3. **最坏情况是静默丢消息**。规则判"这条不重要"就吞掉，用户永远不知道它吞了什么。
   AGENTS §1 的"静默降级不是修复"正是这条红线。

**结论**：本轮不做分析器。若将来要做，前置条件是先拿到"大量消息起了模型但其实不需要"的样本证据——
现在这个数字是 0。

## 3. L3 的三步（按数据排序，每步独立可回滚）

### T1 先把延迟量清楚（必做，其它两步的依据）

现在判断"慢在哪"要靠手写 SQL 查四张表——不可复跑，也没进代码。做成一条命令：

```
feishu-bridge latency [--window 50]
{
  "window": 50,
  "stages": {"collect": {"p50": 27, "p90": 35}, "consumer": {"p50": 13, "p90": 24}, "deliver": {"p50": 5, "p90": 6}},
  "total": {"p50": 53, "p90": 73},
  "scan_interval_seconds": 12,
  "samples": {"answered": 107, "ignored": 33, "dropped": 16}
}
```

同时给消费者那边加分阶段时间戳（claim 到、模型起、模型止、提交）——现在只有 `run.json` 的总时长，
claim→起模型之间那段（CLI 子进程 + 写 prompt + 起 node）是黑盒，只能靠推算。

**判据**：`latency` 输出的分位数与手工 SQL 一致（相差 ≤1s，同一窗口）；消费者日志里四个时间戳
齐全，`模型止 − 模型起` 与 `run.json.duration_seconds` 相差 ≤1s。

**为什么先做它**：T2 调参要能证明有效，T3 要不要做要看 ② 的真实构成。没有它，后面两步都是猜。

### T2 采集提速（已落地，实测结论见下方更正）

`live_interval_seconds` 12 → 3（配置项，改一行，随时改回）。扫描本身是**单次搜索 API 调用**
（`transport.search`：一个 `POST /open-apis/im/v1/messages/search`，`is_at_me=true`），
从 1 次/14s 提到 1 次/4s ≈ 15 次/分钟，远低于接口限额。

> **实测更正（2026-11-05 21:00）**：本节原来的判据「采集 p50 ≤ 6s」是错的，落地时被数据打回。
> 真正的瓶颈是 `Transport._pace(search=True)` 里写死的 10 秒搜索节流（改 `live_interval_seconds`
> 完全无效），而节流去掉之后，剩下的下限是**飞书搜索索引可见延迟 11.1 秒**——search 接口最终一致，
> 采集不可能压到 11 秒以下。修法与最终数字见 [HISTORY §22](../../HISTORY.md)。
> 所以采集的判据改成：**p50 ≤ 13s（= 索引延迟 11s + 一个扫描周期）**，且必须同时给出索引延迟的实测值。

**判据**：`latency` 里 ① 的 p50 ≤ 13s（索引延迟 11.1s 是硬下限）；`search live` 日志间隔 ≤ 5s；
`doctor --assert` 退出码 0、无 230020 限流错误；采集到的消息数不变（同一窗口 `hits` 之和与改前一致）。

**风险与回退**：调高频率只会增加 API 调用，不改任何语义；出问题把配置改回 12 即可。
**不做的部分**：不改用实时事件流——落地时查过 `lark-cli event list`，IM 消息事件
（`im.message.receive_v1`）只声明 `bot` 身份，个人号桥接拿不到；这条路在当前架构下不通，
不是"以后再说"，是"没有入口"。

### T3 「先回执、后答复」（**本人已决定不做，2026-11-05**）

> 拍板结论：现有约 30 秒可以接受，且没有别的优化方法。要再压只能动不可变 outbox 主键，
> 用数据模型风险换体感，在已可接受的情况下不划算。下面保留当初的分析，供以后重新评估时用。

感知延迟的极限：① + 回执路径（≈1s）。如果 T1+T2 之后 ① ≈ 6s、② ≈ 13s，那"先回一句'收到，我看下'"
能把感知从 ~20s 拉到 ~7s，是唯一还能大幅改善体验的做法。

但它有个硬约束：**outbox 的主键是消息 id，一条消息只能有一条回复**
（`INSERT INTO outbox(id, original_id, ...)`，`id = message_id`）。要发第二条"回执"，只有两条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 放宽 outbox | schema v7：主键改 `(message_id, purpose)`，回复带 purpose | 动不可变 outbox 契约 + sender 验证 + 幂等键；风险最高，收益也最高（回执也走持久重试） |
| B. 回执走"回执通道" | 复用教材回执那条路（`transport.reply` 直发，不进 outbox） | 不加 schema；但回执不持久、不重试、`verified` 语义不覆盖它（丢了就丢了） |

**我的建议：先 A 的一半——只对"要跑模型超过 N 秒"的消息发回执，且首选 B**，理由是回执本身就是
"尽力而为"的信息（它不需要被验证投递，用户看不到就当他没在意），不值得为它改不可变主键。
若实测发现回执经常丢（比如发送失败率 >2%），再评估 A。

**判据（无论 A/B）**：发出→用户看到第一条消息 p50 ≤ ①+3s；回执与最终答复**不会让同一条消息的
uuid 撞车**（既有 `reply_uuid(mid, purpose)` 机制要在测试里钉住——本仓历史上恰恰因为
purpose 碰撞留下过一条永久卡住的 outbox 行，见 HISTORY §12）；回执可一键关闭。

### 明确不在本轮

- 内置分析器（§2 已说明为什么）；
- 实时事件流采集（T2 里说明原因）；
- 会话续跑 / 常驻模型进程（D2 决策：回合制；而且实测模型单轮只有 7～12s，不是瓶颈）；
- 并发处理多条消息（现在消息间隔是分钟级，排队不是问题）。

## 5. 测试案例（先写测试再改代码）

`tests/test_latency.py`（新）：
1. 三个阶段分位数与手工计算一致（构造 5 条已知时间戳的消息）；
2. `outbox.verified_at` 为空时用 `sent_at` 兜底，再没有就跳过该样本（不把"没投递"算成 0 秒）；
3. 负数区间（时钟回拨 / 采集时间晚于消息时间）不计入分位数，单独计数；
4. 空库返回 `samples.answered=0`，不抛异常；
5. `--window` 只影响样本量，不影响字段名。

`tests/test_service.py`（新增用例）：
6. 回执只对"预计要跑模型"的消息发，教材私聊/被 ignored 的消息不发；
7. 回执与最终答复的 `reply_uuid` purpose 不同，互不覆盖（回归 HISTORY §12 的坑）。

`tests/test_consumer_runtime.py`（若已有）：
8. 四个时间戳按顺序写入，异常路径（模型失败）也留时间戳。

## 6. 未验证项 / 待拍板

2. **回执方案 A/B 的选择**：需要本人拍板（动不动不可变 outbox 主键）。
3. **② 里 claim→起模型那段到底多久**：现在只能推算，T1 的第 2 步会给准数。
4. 历史数据（108 条全量）混着旧代码与重试，**不能用来代表现状**；本文档所有结论以"最近 8 条 + 24 小时窗口"为准。
